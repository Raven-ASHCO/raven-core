## 0. Decisions on one page

1. **Delivery is pairwise fan-out.** A group message is sealed once per
   recipient, each copy under that recipient's own pairwise session, as an
   ordinary indexed-session Message whose plaintext is an `RVNGRP/1` frame.
   Every copy travels like a chat message: the outbox worker, every carrier
   (LAN, Bluetooth nearby, Internet direct, p2p, friend relay, friend
   custody), the session reset and the long message horizon, the signed
   pairwise ACK. Groups add no carrier and no key.
2. **Every copy is parked, then sealed by raven-node.** A send stages one
   copy per recipient with the horizon's park step (`core/horizon.rs`,
   `IndexedSessionStore::park_outbound` plus the outbound stage) and kicks
   the outbox; the worker's horizon step seals each copy into the session
   with that friend (or pairs first) and sends it. So `raven group send`,
   the terminal app and the desktop apps return at once, and forwards made
   by raven-node itself (item 4) use exactly the same path. This is why the
   groups gate needs the horizon gate.
3. **Authorship is signed.** The author signs `(group id, message id, epoch,
   author key, time, SHA-256 of the body)` with its identity key. A member
   that never shares a session with the author still verifies the message
   with the author's key from the signed roster (item 5).
4. **Bounded forwarding for members the author cannot reach.** The author
   seals copies only to members who are its own contacts. It names the
   others in a `relay` list inside the copy it seals to the group's admin
   (or, if the admin is one of them, inside every copy). A member forwards a
   message only when it got it straight from the author, only to members on
   that list who are its own contacts, and never forwards a forwarded copy
   (one hop). Receivers drop duplicates by message id. In the normal case
   every member gets exactly one copy.
5. **Membership.** A group has a random 16-byte id, a name, one admin (its
   creator) and a roster of at most 16 members, signed by the admin, with
   an epoch that grows by one on every change. Only the admin adds and
   removes; any other member can leave. The admin adds only its own
   friends, so the admin shares a session with every member, which is what
   makes item 4 work. Members learn each other's keys from the roster and
   are never made personal contacts by it.
6. **Receipts.** "Delivered to 3 of 5": a member the author reached directly
   is delivered when that copy's signed pairwise ACK comes (its chat-history
   row turns `delivered`); a member reached through a forward sends a signed
   group receipt back through the forwarder.
7. **Group size cap: 16 members** (the admin included; owner decision
   2026-10-28). Section 7 says why.
8. **Lab only.** `GROUPS_PRODUCTION_ENABLED = false`, lab switch
   `RAVEN_LAB_GROUPS`, plus `RAVEN_LAB_HORIZON` and the Lab Test A unlock. No
   `*_PRODUCTION_ENABLED` gate is flipped.

## 1. Options considered for delivery

| Option | Verdict |
|---|---|
| **Pairwise fan-out** (one sealed copy per member over its pairwise session) | **Chosen.** Reuses every pairwise property: sessions, carriers, custody, horizon, ACKs, link admission. Cost grows linearly with the group; that is acceptable up to the cap. |
| Sender keys (one group key, one ciphertext, distributed pairwise) | Needs a new key schedule, rekey on every removal, and still a pairwise fan-out of the ciphertext because there is no server to post to. A new crypto construction for no saving in a serverless model. Rejected for v1. |
| MLS-style tree (TreeKEM) | The right answer for big groups, but a new crate or a large new construction, and it still needs an ordered delivery service. Out of scope. |
| A member as relay server (everyone sends to one hub) | Violates D1 in spirit (a node becomes the group's server) and makes the hub a single point of failure. Kept only as the fallback in item 4 above, where the admin forwards to the few members an author cannot reach. |
| Flooding (every member forwards everything to every contact in the group) | O(N²) copies per message, every one of them a sealed envelope with a 7-day horizon and possibly a custody deposit. Rejected. |

## 2. What a group is

```text
GroupState (signed by the admin):
  group     16 random bytes
  epoch     u32, 1 at creation, +1 on every change
  name      1..=64 characters
  admin     the admin's identity key (Ed25519, 32 bytes)
  issued    the admin's clock at signing (ms)
  members   1..=16 entries, admin first: { key: identity key, label: 0..=64 chars }
  sig       Ed25519 by `admin` over the canonical bytes (protocol §3.1)
```

- **Admin model.** One admin, the creator, for the life of the group. The
  admin cannot leave (it would orphan the roster); it can remove every other
  member. Hand-over and several admins are owner decisions (section 11).
- **Labels.** A member's `label` is the name the admin gave that friend. It
  is shown to members who do not have that person as a friend; a member who
  does sees its own name for them. Labels are visible to every member
  (section 9).
- **Epochs.** A receiver keeps the newest roster it verified. An older or
  equal epoch is ignored (an equal epoch with other content is counted as an
  admin conflict and ignored). The roster is never merged.

### 2.1 Operations

| Operation | Who | What is sent |
|---|---|---|
| create | anyone (becomes admin) | roster epoch 1 to every member |
| add | admin | roster epoch e+1 to every member, the new ones included |
| remove | admin | roster epoch e+1 to every remaining member and to the removed ones (so they know) |
| leave | any member but the admin | a signed `leave` to the admin, which then sends roster e+1 without the member |
| send | any member | one `msg` copy per member it has as a friend (section 4) |

Adding requires each new member to be one of the admin's current,
unblocked friends (`raven_core::outbox::contact_admission` is `Allowed`), so
the admin can always seal to every member. Removing a member is immediate for
the admin and takes effect for everyone else as the new roster arrives.

## 3. How a frame travels

A group frame is the ATSAM plaintext of an indexed-session Message, exactly
like an `RVNAPP/1` app frame (`protocol/RAVEN_APP_PAYLOAD_V1.md`). The
receive side plugs into the same three points as the app channel
(`core/app_channel.rs`), so every carrier gets it at once (LAN dispatch,
Internet direct, p2p and nearby links through `lan_dispatch`, friend relay
and custody through `relayed_ingest`):

1. **Before commit** (`inbound_policy`, ATSAM_ENDPOINT_TRANSACTION_V1 §1
   step 7): a plaintext that starts with `RVNGRP/` is *deferred* (nothing is
   committed, no ACK, the sender retries the same bytes) when the gate is
   closed or the frame does not parse strictly. Otherwise it is accepted.
   No store is read here.
2. **After commit** (`deliver_committed`): the frame goes to the group store
   (`core/group.rs`), never to chat history. `Ok(false)` (the store could
   not be written) sends no ACK; the endpoint inbox row stays durable and the
   next copy, `ingest_pending_committed` or the expiry archive
   (`archive_inbox_row`) stores it later. Ingest is idempotent.
3. **Inbox listings** (`raven inbox`, the deletion tombstones) already skip
   every plaintext that is not `PayloadClass::Chat`; a group frame is
   `PayloadClass::Group`.

The pairwise peer that handed the copy over (the session-bound certificate's
`user_ed_pub`, never a link bundle) is the frame's *carrier peer* below.

### 3.1 Sending: park, then the worker

`group::park_copy` does for one recipient what `ash`'s `park_new_message`
does for a chat message to an unreachable friend, under the friend's
`PeerSendLock`:

1. the recipient must be an admitted contact; its device key comes from its
   cached certificate (else its identity key, a primary device's);
2. room: fewer than 32 messages waiting for that friend (prepared, sent
   without an ACK, or parked), and the outbound stage under the groups'
   share (section 7);
3. `park_outbound(device, mid, None, now, deadline, now)` with the horizon's
   7-day deadline, then the body staged with the sentinel binding and a
   `queued` history row (`ensure_outbound_queued_history_under_send_guard`);
4. the route record `CarrierChoice::Auto` with no routes (the worker plans
   the friend's routes at each attempt, as AppSubmit does), `unsent`, and
   friend custody when its gate is live;
5. the outbox is kicked (raven-node: in process; ash and the engine: IPC
   `OutboxKick`).

The worker's horizon step then seals the copy into the newest sendable
session with that friend, or pairs first (one PairInit per step, the shared
re-pair budget), and the normal attempt sends it. Delivery, retries, custody,
expiry after 7 days and the ACK are the chat message's.

**Chat views.** A sent copy has a chat-history row (`out`, its body the
frame) while it travels, which the horizon and the ACK path need. Every chat
view (`raven messages`, the terminal app, the engine's `messages.history`,
contact previews, `raven outbox` previews) leaves out rows whose body starts
with `RVNGRP/`; the composers refuse chat text that starts with it, as they
refuse `RVNAPP/`. Once a copy's row is final (`delivered`, `failed`,
`expired`, `cancelled`) the group store keeps its state and the row is
deleted (`group::refresh_deliveries`), so group traffic never pushes 1:1
chat out of the history's 2,000 rows.

## 4. Messages and forwarding

### 4.1 The author

For a group at epoch `e` with roster `M` and the author `A`:

1. `id` = 16 random bytes; `sig` over the canonical bytes (protocol §3.2).
2. `targets = M \ {A}`; `direct = targets ∩ A's admitted contacts`;
   `relay = targets \ direct`.
3. Forwarders: if `relay` is empty, none. If the admin is in `direct`, the
   admin alone. Otherwise (the author is the admin, or the admin is in
   `relay`) every member of `direct`.
4. One copy per member of `direct`; the copy to a forwarder carries
   `relay`, every other copy carries `[]`. `relay` is outside the signature:
   it is an instruction from the author to that one recipient, authenticated
   by their pairwise session.
5. The group store records the message with one delivery line per target:
   `direct` (with the copy's message id) or `relay`.

In the normal case only the admin learns which members the author could not
reach.

### 4.2 A receiver

A `msg` from carrier peer `P` is accepted when all hold:

- the group is known, this profile is an active member, and the author is in
  the current roster (a removed member's messages are dropped, whatever
  epoch they claim: the epoch is the author's own word);
- the signature verifies under the author's key from the roster;
- its id is new for the group (else: a duplicate, stored once, still ACKed).

When the author is not in the roster but `epoch` is newer than the roster,
the frame is **held** (at most 64 per group, 7 days) and a `sync` request
goes to the admin (at most one per group per hour). A frame for a group this
profile does not know yet is held the same way (at most 32 in all), because
the roster and the first message travel independently. Whenever a newer
roster is stored, held frames are tried again.

**Forwarding** (only when `P` is the author, so `relay` is the author's own
word): for each `T` in `relay` with `T` in the roster, `T` not this profile,
`T` an admitted contact of this profile, a forward of the same signed
message with `relay = []` is queued once. A copy that came from anyone other
than its author is never forwarded (one hop), whatever its `relay` says.

**Receipt for a forwarded copy** (`P` is not the author): a signed
`receipt` (protocol §3.3) to the author is queued and sealed to `P` with
`relay = [author]`; `P` forwards it to the author under the same rule (it
came straight from its signer, the author is on its `relay` list and is
`P`'s contact). The author marks that member delivered. Members reached
directly need no group receipt: the pairwise ACK of the copy says it.

### 4.3 Work raven-node does later

The receive path has no identity key and must not dial, so it only records
**intents** in the group store (durable, with the rest of the group's
state): forwards (the frame is ready), receipts to sign, a roster to publish
(the admin after a `leave`), a roster to send back (the admin answering a
`sync`), a `sync` to send. `group::run_pending(data_dir, identity, now)`
turns them into parked copies. raven-node runs it in its outbox scan (a
receive that records an intent asks for a scan at once through
`group::set_work_notifier`); `raven group` commands, the terminal app and
the engine run it too. An intent that cannot be parked now (the friend's
send lock is busy, no room) stays and is tried again; one that never can
(the target is no longer a friend or a member) is dropped and counted; every
intent ends 7 days after it was made.

### 4.4 Delivery states shown

Per member of a message this profile sent:

| State | Meaning |
|---|---|
| `waiting` | the copy is queued or parked here (not on the wire yet), or the member is reached through a forward and no receipt has come |
| `sent` | the copy left this computer; no ACK yet |
| `delivered` | the member's Raven confirmed it: the copy's signed pairwise ACK, or the member's signed group receipt |
| `failed` | the copy was given up (no longer a friend, revoked lineage, or 7 days passed) |

The message line says "delivered to *d* of *n*". The direct states come from
the copy's chat-history row (`queued`/`sent`/`delivered`/`failed`/`expired`),
read when a group view is built and kept in the group store once final.

## 5. Membership details

- **Create** (`group::create`): name, labels and up to 15 friends; each must
  be an admitted contact. The roster at epoch 1 goes to every member.
- **A new roster reaches a profile** from its carrier peer `P`:
  - unknown group: accepted only when `P` is the roster's admin (an
    invitation comes from the admin itself, who is a friend) and this
    profile is in the roster; at most 64 groups;
  - known group: the signature must verify under the group's admin key
    (fixed at creation), and the epoch must be newer;
  - this profile not in the new roster: the group turns `removed` (its
    history stays, nothing more is sent or forwarded);
  - members that left the roster are remembered as removed.
- **Leave** (`group::leave`): the member signs a `leave` for the current
  epoch and seals it to the admin; locally the group turns `left` at once.
  The admin, on a verified `leave` from a current member, publishes the next
  roster without it.
- **Sync**: a member who sees a newer epoch than it holds asks the admin;
  the admin answers a current or removed member with its newest roster, at
  most once per member per group every 10 minutes.
- **Keys of non-friends.** The roster introduces every member to every
  other one. It meets the admission rules of
  `protocol/RAVEN_INTRODUCTION_V1.md` (the introducer, the admin, is a
  non-blocked contact; the recipient is this profile, which is on the list),
  but it is not encoded as `RavenIntroductionV1` records: those are one per
  recipient with an encrypted note and an expiry (N² records per change,
  and a roster must not expire). The member keys stay in the group store and
  are never written to the contact book. Making a member a personal friend
  is the normal add-and-verify flow (`raven contact add` with their card and
  the security words); the contact-request transport
  (`RAVEN_CONTACT_REQUEST_V1.md`) is on security hold and is not used.

## 6. Storage

`groups.json` in the profile, at-rest kind `Groups` (144, a lane of its own
from 144 up), sealed in a sealed profile, plain before, under its writer lock
`.at_rest.groups.lock.sqlite`; `raven erase` deletes it. One file holds every
group: roster, status, messages with their delivery lines, ids seen, held
frames and intents.

| Bound | Value |
|---|---|
| Groups | 64 |
| Messages kept, all groups | 2,000 and 8 MiB (oldest message of the largest group goes first) |
| Ids remembered after a message left | 4,096 per group (duplicate drop) |
| Held frames | 64 per group, 32 for unknown groups, 7 days |
| Intents | 512 per group, 7 days |
| Body | 1..=8,192 bytes of chat text |

Chat keeping (`raven chats keep`) and "delete chat" do not touch groups in
v1; `raven group leave` keeps the history. Both are follow-ups (section 12).

## 7. Why the cap is 16

The owner chose 16 (2026-10-28; 32 was the first proposal). The cost of
one message grows with the group, and every copy is a full pairwise object:

- **Fan-out at the sender:** N−1 seals, N−1 dials (or custody deposits) and
  N−1 ACKs per message; at 16 that is 15 of each. A forwarder adds at most
  N−2 more for one message, normally only the admin.
- **The outbound stage** keeps each copy's body until its ACK. It holds 256
  entries and 4 MiB in all (`core/chat_history.rs`), shared with 1:1 chat.
  Groups may fill at most half of it, 128 entries (`GROUP_STAGE_BUDGET`;
  160 while the cap was 32): 1:1 chat keeps the other half, room for four
  friends' full queues of 32. At 16 members that is eight messages to an
  all-offline group before `raven group send` says to wait
  (`GROUP_QUEUE_FULL`); the budget no longer needs to stretch for 31-copy
  messages, so half is the simple, safe share.
- **The per-friend queue** (`MAX_QUEUED_PER_PEER = 32` in ash) also counts
  group copies.
- **The roster** stays well inside one frame at 16 (about 3 KiB).
- Beyond a few dozen members a group needs a different construction (sender
  keys or a tree), not a bigger fan-out.

## 9. Privacy

**What members learn about each other.** Every member sees the group id,
its name, every member's identity key and the admin's label for each
member, and the admin. A member also learns, for each message, its author,
time and text, and (from receipts and forwards) that some members are not
friends of some others: in the normal case only the admin learns which
members an author cannot reach (section 4.1); in the fallback every member
the author reached learns it.

**What carriers and custodians see.** Nothing new beyond pairwise traffic:
each copy is an ordinary sealed envelope between two friends. A group
message produces up to N−1 envelopes from the author at about the same time
(plus forwards), so an observer that sees many links at once can correlate
a burst. Link padding (where enabled) hides sizes, not timing. Friend
custodians hold sealed objects only.

**Limits.**

- **No forward secrecy beyond the pairwise sessions.** A group adds no keys:
  a copy is as safe as the session it was sealed in (24 h sessions, no
  ratchet inside one; `docs/design/2026-10-ratchet-fs-pcs.md`).
- **Signed authorship is transferable.** The author's identity-key signature
  over the body hash lets any member prove to anyone else that the author
  wrote that text. Pairwise chat has no such signature. This is what makes
  forwarding to non-friends possible without a server; owner decision.
- **A removed member keeps what it received.** Removal only stops new
  messages, once the senders and forwarders hold the new roster; a sender
  with an older roster can still send to a removed member until the new
  roster reaches it.
- **The admin is trusted for membership.** It can add anyone it is friends
  with and could show different rosters to different members; v1 does not
  detect that beyond the equal-epoch conflict counter.
- Group data at rest follows the profile's at-rest mode (sealed or plain).

## 10. Tests

- Core: frame codec and limits; signature domain separation (no group
  signing input starts with the AgentSign prefix); roster rules (unknown
  group only from its admin, epochs, removal); message acceptance
  (non-member, removed member, tampered body, wrong signer, duplicates,

  hop); receipts; caps; the `RVNGRP/` composer guard and chat-view filter;
  `park_copy` against a real session store.

- CLI and terminal app: commands and screens on lab profiles.
- Engine: the ops on lab profiles; **three real raven-node processes on
  127.0.0.1** where A and C are not friends but both are B's: B (admin)
  creates the group, A's message reaches C only through B's forward, C
  verifies A's signature from the roster, C stores it exactly once, and A
  sees C delivered by C's receipt.
- Apps: none in this branch (their group screens come with the new app
  design).

## 11. Owner decisions (decided by the owner, 2026-10-28)

1. **Group size cap: 16 members**, the admin included (section 7). The
   first build had 32.
2. **Admin model: one admin, the creator, who cannot leave**, as built.
   Not taken: hand-over, or several admins (each adding its own friends,
   forwarding following the member's sponsor).
3. **Signed authorship: accepted**, as built (section 9): a member can prove
   to anyone who wrote a group text. Not taken: groups only of members who
   are all friends of each other (no forwarding, no signature).
4. **Who may forward: the admin first, with every recipient as the
   fallback**, as built. Not taken: every recipient always (more copies,
   faster while the admin is away).
5. **Invitations: joining is automatic** when a friend adds this profile, as
   built (the user can leave at once). Not taken: an explicit accept step.
